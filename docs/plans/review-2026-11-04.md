## A. Bugs (confirmed with a throwaway test, since deleted)

**A1. A later status change wipes a player's earlier status, which skews stats and fairness.** M
Each player has only one status (`game.statuses[id]`), so a new one replaces the old one ([changes.ts:207](../../src/domain/changes.ts:207)). Cases:
- A late arrival who is later rested or ruled out loses the "arrived" record. Their segments before arriving then count as **Sat** on the Final screen and in season %. Confirmed: arrive at segment 5, rest 1 → *Sat 4* instead of 0.
- **Available again** is shown while "Arrived, plays from …" is showing. Tapping it deletes the arrival, and the engine then thinks the player missed 4 segments and gives them catch-up time. Confirmed: 3 of the remaining segments instead of a fair 2.
- Rested, then **Available again** partway through the rest, or rested and later ruled out: the rested segments that already passed turn into "sat".

*Fix:* keep a list of status intervals per player, so a change only affects segments from the next one on. "Available again" ends the current interval instead of deleting history. This needs a schema v4 migration (turn the single status into a one-item list) and tests. Alternatively, freeze availability into each played segment's record at Next.

**A2. A game-day "send in someone else" swap can be undone by a later re-plan.** S
`swapNext` changes the next lineup but doesn't keep the swap as a lock ([changes.ts:187](../../src/domain/changes.ts:187)), unlike the plan screen's swaps. A re-plan after a later injury is free to put the old player back. Confirmed: the coach's swap was reverted. D6 says a re-plan "keeps manual edits". *Fix:* add an in-lock for the incoming player and an out-lock for the other, as `swapInPlan` does.

**A3. The "Update available" banner doesn't react to navigation.** S
It checks `window.location.hash.endsWith('/live')` only when it renders, and it doesn't re-render on navigation ([UpdateBanner.tsx:18](../../src/components/UpdateBanner.tsx:18)). If an update arrives on the Teams screen, the banner stays up after the coach opens Game Day. It also shows on the Teams screen while a game is live, and tapping **Update** reloads mid-game. T8 says the prompt is hidden while a game is in progress. *Fix:* subscribe to the route, and hide the banner whenever any game has status `live`.

**A4. The skill-balance rule (R3) scores one thing and builds another.** S
The generator counts a player's *best* skill at any position ([generate.ts:170](../../src/engine/generate.ts:170)). The scorer and the warning count the skill at the *assigned* position ([analyze.ts:62](../../src/engine/analyze.ts:62)), which is what R3 says. A player who is Go-To at Guard but Rising at Center, placed at Center, looks fine to the generator. The plan then shows a "skill-stack" warning the generator never tried to avoid. *Fix:* use the assigned position's skill in the generator, or pick positions before costing the lineup.

**A5. Roster chips aren't in G, F, C order.** S
The Roster tab lists positions in the order they were tapped in the editor (`Object.entries(p.skills)`, [TeamScreen.tsx:92](../../src/screens/TeamScreen.tsx:92)), so one player shows "C G" and another "G C". The substitute picker already uses the team's order. This folds into D1.

## B. Gaps against the requirements

**B1. A game can't be ended early (D9).** S
**End game** only appears on the last segment. If time runs out with segments left, the coach has to tap **Next** through them, which records lineups that never played, inflates stats and logs nothing. *Fix:* add **End game now** to the Game Day **Edit** menu (after confirming). It ends without recording the remaining segments, and **Undo end of game** still works.

**B2. There's no way to see the rest of the plan during a game.** S
Game Day shows only the current and next lineups. The Plan screen works read-only for a live game, but nothing links to it: the Edit menu → **Game setup** only offers "Back to game". *Fix:* add **See full plan** to the Edit menu, so the coach can answer "when am I in?" at a timeout.

**B3. D4 says "change the current lineup or any upcoming lineup"; only current and next are possible.** M
Allow taps on later segments in the read-only plan view during a live game, using the same swap and lock logic (with D3 still protecting played segments). Or record it as a decision that current and next are enough.

**B4. Deleting a player erases their history (M3).** S
**Remove player** hard-deletes ([PlayerSheet.tsx:76](../../src/screens/PlayerSheet.tsx:76)). Past Final screens then show "Unknown", and season stats drop the player. M3 says inactive players keep their history. *Fix:* when a player has any games, offer only **Mark inactive**, or say plainly what's lost. Allow a true delete only for players with no games, such as a typo.

**B5. Jersey numbers aren't shown in the IN/OUT pairs, and duplicate names aren't caught.** S
§13 asks for prominent jersey numbers, but the "Next change" pairs show only names. With two players named Sam, the pairs are ambiguous. *Fix:* show the jersey in the pairs, and warn in the player editor when a name is already on the roster.

**B6. The wake lock fails silently (D7, risk register).** S
If `navigator.wakeLock` is missing or refused, nothing tells the coach. The risk register plans a fallback hint. *Fix:* show a one-time note on Game Day: "Your screen may lock. Set Auto-Lock to Never during games."

**B7. Games aren't grouped by status (S2).** S
The Games tab is one list by date with a status badge. Put **In progress** first, then **Upcoming** (soonest first), then **Finished**.

## C. Robustness and hardening

**C1. Game Day writes from the on-screen copy of the game, which breaks a CLAUDE.md rule.** M
**Next**, **Undo**, swaps and overtime call `saveGame(fn(game))` with the rendered copy ([GameDayScreen.tsx:310](../../src/screens/GameDayScreen.tsx:310)). Plan editing reads the latest saved copy first (`getGame`). Two real risks:
- A double-tap on **Next** about 100–300 ms apart (after the first save re-renders) advances two segments.
- **Next** then **Undo** tapped before the re-render undoes from the old copy and drops a played segment.

*Fix:* add a `mutateGame(id, fn)` in `repo.ts` that reads, applies and writes in one Dexie transaction, and use it for every game-day action. Also ignore **Next** taps for about 600 ms after one, with a short visual confirmation.

**C2. Game Day has no Undo for swaps and status changes.** M
A mis-tapped **Sub out now** credits both players for the segment, and swapping back leaves three players credited. Only **Next** can be undone (D2). *Fix:* an undo snapshot like the plan screen's "↶ Undo" notice, covering the last swap or status change.

**C3. "Replace everything" with a one-team backup silently deletes your other teams.** S
The confirm says "Replace all teams and games" ([SettingsScreen.tsx:59](../../src/screens/SettingsScreen.tsx:59)), but it doesn't say which teams on this phone aren't in the file. *Fix:* name the teams that will be deleted. Optionally save an automatic "before restore" backup first.

**C4. Received links and files are only lightly validated.** S–M
`parseHandoff` and `parseBackup` check ids and formats, not shapes. A malformed or crafted file can crash a screen. For example, a requirement of `{ G: 1e9 }` makes `requiredSlots` loop a billion times and freeze the app ([positions.ts:7](../../src/engine/positions.ts:7)). *Fix:* a small hand-written schema check (formats, segment counts, a requirement of 5 or less, lineups of 5 or 6 known players). Clamp `requiredSlots` in any case.

**C5. A received game can overwrite this phone's team.** S
If the incoming team record is newer, `receiveGame` replaces the local team's name, requirement, defaults and **archived** flag. *Fix:* update only what the game needs (requirement and positions), or keep the local team when it already exists.

**C6. Typed text can be lost when the phone locks.** S
Opponent and team name save on blur. Locking the phone or switching apps mid-typing may never fire blur on iOS. *Fix:* also save after a pause in typing (debounced) or on `visibilitychange`.

**C7. Small cleanups.** S
- `playingTime` in [game.ts:166](../../src/domain/game.ts:166) is used only by tests, and it counts the current plan rather than `startPlan`. Remove it, or point the tests at `gameStats`.
- `isStandalone` is duplicated in `InstallHint.tsx` and `viewport.ts`.
- The "Playing time isn't equal" warning always blames position coverage, even when the cause is the coach's locks. Name the locks when they're the cause.

## F. Changelog, release philosophy and version numbers (your request)

**What happens today:** every push to `main` that passes CI deploys straight to coaches. `package.json` has said `0.1.0` since the first commit, there are no git tags, and Diagnostics shows only a build time. Coaches can't tell what changed, and you can't hold merged work back from them.

**Proposed philosophy**
- **Merging isn't releasing.** Work merges to `main` as now. A *release* is a deliberate step you approve, and only releases deploy to GitHub Pages. That gives you a window to test `main` on your iPhone before coaches see "Update available", and it batches updates so coaches aren't prompted after every small PR.
- **Every change says what it means to a coach.** Each PR adds a short changelog note in plain coach language, which becomes the in-app "What's new".

**Numbering (semantic x.y.z)**
- **z, patch:** fixes, polish and internal changes. This is the default.
- **y, minor:** a new feature or requirement a coach would notice (a new screen, rule or action).
- **x, major:** something a coach must act on or that breaks compatibility. For example, a backup or shared-game format an older app can't read ("update both phones"), a data change that can't be rolled back, a removed feature, or a big redesign.
- **Stay on 0.x** until you call v1 done, then release **1.0.0** as a milestone. The v1 goals look nearly complete; a likely trigger is after the accessibility pass, the first-run guide and a real game or two.
- **Claude never chooses x or y on its own.** When notes include a new feature, Claude proposes minor and asks you. Major is always your call.

**How it would work**
1. **Changelog notes.** Each PR adds `changes/<short-name>.md` with a type (*New*, *Improved*, *Fixed*) and one or two coach-facing lines. A CI check fails a PR that changes `src/` without a note, unless it carries a `no-changelog` label for tests or docs only.
2. **Release PR, with the prompt to you.** When there are unreleased notes, Claude asks: *"3 unreleased changes, 1 new feature. Release as 0.2.0 (minor), or 0.1.1 (patch)?"* Claude then runs `npm run release -- minor` (a new `scripts/release.mjs`). The script bumps `package.json`, folds the notes into `CHANGELOG.md` and a `src/changelog.json` the app reads, and deletes the notes. Claude opens that as a normal PR, so the required CI checks run. Your ruleset requires status checks on `main`, which is why a CI job can't push the bump directly.
3. **Merging the release PR deploys.** When a push to `main` changes the version, CI tags `vX.Y.Z`, creates a GitHub Release from that version's changelog section, and deploys. Pushes that don't change the version run CI but don't deploy. CI also checks that the version only goes up and that `CHANGELOG.md` has a section for it.
4. **In the app.**
   - The update banner names the version and its first headline, e.g. "next5 0.2.0 is ready: share a game by QR code".
   - After updating, a one-time **What's new** sheet appears, never during a live game.
   - Settings gets **What's new** with the full history.
   - Diagnostics shows the version plus the short commit.
5. **Docs and memory.** Add requirement rows (new IDs such as REL1–REL4) and a decisions-log entry. Add a CLAUDE.md rule: every PR adds a changelog note, and Claude asks before minor or major bumps.

*Alternatives considered:* **Changesets** and **release-please** both work, but their bots open PRs with the default token, and those PRs don't trigger the required CI checks without a personal token or GitHub App. release-please also builds notes from commit messages, which are developer language. The script above is about 100 lines with no new dependency.

*Decision for you:* deploy only on releases (recommended), or keep deploying every merge and use releases just for numbering and notes.

## G. Tests and tooling

**G1. A property test that runs random game-day sequences.** M — the most valuable test to add.
Use fast-check's model-based commands to apply random sequences of Next, Undo, swap now, swap next, status changes, late arrivals, re-plan and overtime to random rosters. After every step, check:
- played segments never change
- every lineup has 5 distinct attending players
- for each player, played + sat + unavailable equals segments played
- coach swaps and locks survive re-plans
- Undo is the exact inverse of Next

A1 and A2 would have failed this test.

**G2. Regression tests for A1–A4 and B1**, written to fail before the fix.

**G3. A performance test at the largest allowed format.** S
Today's N2 check uses 16 segments. The settings allow 6 segments per quarter (24 segments, plus overtime) with 15 players and every rule on. Test that size, or cap segments per period lower.

**G4. Small test gaps.** S
`UpdateBanner` is at 70% (and see A3), `useWakeLock` has no test for re-acquiring when the app returns to the foreground, and `db.ts` lines 57–60 (`requestPersistentStorage`) are untested.

**G5. A faster unit test run.** S
The unit tests take about 3 minutes, and nearly half of that is creating jsdom 21 times. Try Vitest's `pool: 'vmThreads'`, or run the engine and domain tests in the `node` environment. That makes `npm run check` much faster for every change.

**G6. CI tidy-ups.** S
- Dependabot for npm and GitHub Actions.
- Avoid running CI twice for PR branches (`push` *and* `pull_request`).
- Build once and deploy the same files the e2e tests ran against (this fits F3).
